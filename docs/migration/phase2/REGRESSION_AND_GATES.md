# 功能保留清单与阶段门槛

阶段1：用户于2026-10-28在本聊天明确确认恢复副本三角色登录、社区/通知、工作区和导航全部通过。此确认不代表下述新微服务功能已实现或验收。

阶段2：静态设计检查；以下实施场景当前均 NOT_RUN，后续按阶段逐项给证据，不以设计文档标 PASS。

## 用户逐项核对

- [ ] 登录、注销、三角色、停用账号、强制改密和 CSRF 行为保持。
- [ ] 社区列表、分类、字面搜索、LATEST/UNANSWERED/SOLVED、稳定分页与空结果提示。
- [ ] 我的问题/我的回答两个页签，编辑/撤回后的筛选和分页跳转保持。
- [ ] 问题发布/修改/撤回、正文转义、作者和非作者访问规则保持。
- [ ] 回答发布/修改/撤回、采纳/取消采纳/重新采纳；不可自采纳。
- [ ] 隐藏/撤回内容的可见性及占位正文，不暴露他人隐藏内容。
- [ ] 2分钟重复问题检测；问题和回答分别24小时20条上限，跨实例仍成立。
- [ ] 举报问题/回答、重复举报拒绝、原因及文字校验保持。
- [ ] 管理员 OPEN/HANDLED/ALL 队列、处理理由、独立 hideContent、隐藏/恢复、历史与全局分页保持。
- [ ] 审核与社区本地审计原子保存；原统一审计页仍含非社区记录，不重影、不漏页。
- [ ] 回答、采纳、隐藏通知正确收件人、未读/已读和旧链接保持；自答不自通知。
- [ ] 报修照片、提交、审核、指派/改派/撤回、维修记录、确认、关闭、反馈、退修与重开回归。
- [ ] 设施地图、仪表盘、公告、账号管理和 SLA 未因社区拆分回归。
- [ ] 原版及恢复保护实例仍保留，关闭迁移环境不影响它们。

## 自动验证分配

阶段3：独立构建/数据库凭据隔离/健康检查/禁止原资源配置。阶段4：身份与权限、PostgreSQL发帖并发。阶段5：最小业务链路、幂等和事件失败。阶段6：全社区、审计、页面消费契约。阶段7：历史数据/序列/水位/新写入回退。阶段8：完整回归、真实两个进程竞争、独立发布及故障隔离。阶段9/10：受控负载和扩容收益，不能用功能通过代替。

新增API开发前，固定每个现有HTML路由与contracts.json的映射；表单路由仍留Core。没有API实现时不运行“模拟成功”来认证可部署。

性能初始目标沿用既有建议：每个关键端点p95<=1秒、p99<=2秒，非预期业务/协议错误<1%，认证失败0；属于工程目标。输入速率、实际成功业务吞吐、内容校验和dropped_iterations都记录。相同到达率的吞吐相同不等于扩容失败；容量曲线和资源瓶颈必须一起分析。

阶段2通过条件：全部浏览器路由有映射；数据依赖逐项有归属和替代；API/事件/错误/身份/幂等一致；新ADR不抹历史；只提交安全文档；main/基线/业务代码未变化。

进入阶段3前请用户确认本清单无遗漏。阶段2完成不自动启动阶段3，不声称已交付微服务或证明扩容收益。
