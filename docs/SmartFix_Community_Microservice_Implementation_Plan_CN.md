# SmartFix 社区微服务迁移与扩容验证实施计划

日期：2026-10-27（Asia/Shanghai）。状态：实施计划；本文的新增不表示迁移、部署或压测已经完成。

## 交付目标与表述

形成 Core 与 Community 两个可独立部署的业务服务，实际落地社区数据所有权、API/事件通信以及社区独立水平扩容。Core 内部继续采用模块化组织，保留维修业务的事务边界。

没有仅按服务数量判断微服务的标准；两个符合上述条件的业务服务足以展示微服务演进。两个容器、两个实例、两个 Maven 模块本身不是证明。由于原 Core 仍承载多个业务能力，答辩准确表述为“通过社区服务抽离，实现从模块化单体向微服务演进”，而不是“全部业务已完全微服务化”。

架构成立、扩容机制可用、扩容性能收益以及教师评分是不同问题。前两项可设置工程验收门槛；性能必须实测；不能预先保证评分或线性性能增长。

## 目标拓扑

浏览器 → Core 页面/登录入口 → 社区内部负载均衡 → Community 实例 1…N → Community 数据库。

Core → Core 数据库；Core 不连接社区数据库，Community 不连接 Core 数据库。

社区业务事务 → Community 本地 outbox → 发布器 → Core 内部事件接收 API → Core 通知任务/审计查询投影。

Core 在第一轮社区扩容实验中固定为一个实例。发布器是社区应用的一项组件，不必算作第三个业务服务。负载均衡器、数据库和测试工具也不计入业务服务数量。

## 第 1 步：保护现有工作并建立版本基线

动作：
- 记录当前分支、提交 SHA、工作区变更清单；当前工作区已有未提交修改，禁止 reset、清理或覆盖它们。
- 保存可以重新构建的迁移前代码基线；基线包含未提交改动时，记录补丁或快照摘要，不能仅写 HEAD。
- 使用隔离的测试数据库运行现有单元、Web、集成与原生 PostgreSQL 检查；记录实际执行的命令和环境。现有 pom 提供 postgres-it，但不得指向正式数据运行测试。
- 将迁移前已有失败与本次引入失败分开记录；不把旧结果当作当前代码通过。

产物：baseline.md、测试输出、环境和构建摘要。通过条件：能重建基线，未损失原有修改，已知哪些功能当前正常。

## 第 2 步：冻结功能验收清单和性能口径

动作：
- 社区验收覆盖列表、搜索、分页、我的问题/回答、详情、发布/修改/撤回、采纳/取消采纳、举报、审核、隐藏/恢复、历史和审计。
- 覆盖 REQUESTER、TECHNICIAN、ADMINISTRATOR；包括所有权、隐藏内容可见性、停用账号、强制改密、注销和 CSRF 行为。
- 通知覆盖正确收件人、未读数、已读、跳转、重复事件和失败恢复。
- 核心回归覆盖报修、照片、审核、指派/改派/撤回、维修、确认、关闭、反馈和重开。
- 测试前固定场景目标。建议初始工程目标为各关键端点 p95 ≤ 1 秒、p99 ≤ 2 秒、非预期业务/协议错误率 < 1%；这些是待确认的验收目标，不是已测得能力或正式生产 SLA。
- 单独记录预期拒绝、认证失败、业务错误、HTTP 5xx、超时和内容错误；HTTP 200 但实际是登录页不算成功。
- 约定事件恢复和通知可见性目标，并与原体验比较。异步不能被解释为无限延迟；社区审核审计仍须和审核事务一起成功或回滚。

产物：逐项可执行的验收清单、固定的性能策略。通过条件：每项都有输入、角色、预期页面/数据及可核对结果。

## 第 3 步：明确业务边界，更新架构决策

动作：
- Core 拥有账号认证、角色、账号状态、报修、派工、工单、现阶段 SLA、通知中心、现有页面和非社区审计。
- Community 拥有问题、回答、采纳关系、举报、审核、社区审计、社区发帖控制记录、事件 outbox 和写操作幂等记录。
- 页面控制器和模板可以留在 Core，但只负责展示、请求转换和调用 API，不保留社区状态决策或 SQL。
- 按实际代码列出跨边界依赖：CommunityAccessGuard → UserService；CommunityQueryService → 用户显示名；CommunityModerationService → AuditService；社区事件 → CommunityNotificationListener。
- 创建新的 ADR，说明范围调整以及它替代 ADR-001 中“独立服务不在范围内”的部分；保留原决策历史。
- 允许共享小型通信契约，但禁止把实体、Repository 和整个业务模块打成公共 JAR 让两端共用。

产物：数据所有权清单、依赖清单、新 ADR 和目标拓扑。通过条件：每个数据项和业务规则只有一个负责的写入服务。

## 第 4 步：先定义 API，再移动业务代码

动作：
- 编写版本化的内部 API 契约，覆盖查询、详情、问题写入、回答写入、采纳、举报、审核、历史和社区审计。
- 定义 actor 来源、输入校验、筛选条件、分页上限、排序稳定性、HTTP 状态和业务错误码。
- 保持原来的 403/404/冲突语义及页面映射；不让隐藏内容通过 API 泄露。
- 定义写请求的幂等键，社区将幂等记录与业务写入放在同一事务中。明确同一键不同请求体的拒绝规则。
- 网络超时不意味着写入失败。禁止无幂等保障自动重试 POST；设计按幂等键查询结果或安全重试的方式。
- 旧页面 DTO 和服务间 DTO 分离，不把 JPA 实体或框架内部异常作为通信协议。

产物：OpenAPI/JSON 示例、错误和幂等规则、消费端契约检查。通过条件：Core 可以用模拟响应验证页面映射，Community 可以按同一协议实现。

## 第 5 步：建立独立 Community 应用

动作：
- 建立独立启动入口、构建目标、配置、数据库账号、Flyway 目录、部署包、健康检查和版本信息。
- 可以保留同一个 Git 仓库。若使用 Maven 聚合构建，确保每个服务可以单独产出和部署包，不要求另一个服务同步发布。
- 第一阶段可使用同一 PostgreSQL 服务器的两个独立数据库和不同角色；记录共享 CPU/I/O 的限制。不要把两个 schema 简单误称为两台数据库服务器。
- Community 配置仅包含自己的数据库连接，Core 配置不包含 Community 数据库凭据。
- 迁移前仍保留旧运行路径；新服务先接测试数据，不直接接管正式流量。

产物：两个独立构建产物、本地启动配置、服务版本与健康信息。通过条件：Community 可以单独构建、启动、停止。

## 第 6 步：解除数据库外键和账号行锁耦合

动作：
- 核对 V17/V18/V19 及后续全部迁移，查清问题、回答、举报、采纳、约束和索引最终状态。
- 新社区数据库中的 author_id、reporter_id、handled_by_user_id 等作为外部账号引用；不再创建跨数据库 users 外键，不复制密码等认证数据。
- 保留社区内部的外键、采纳答案所属问题约束、唯一索引、乐观/悲观锁和审核并发规则。
- 当前 serializePosting 会调用 users.lockActivePostingAccount；改为锁社区自己的用户级发帖控制记录。控制记录首次创建也要有唯一约束并处理并发创建。
- 发帖/回答的频率控制、重复内容检查和保存应在可解释的本地事务边界内执行；测试多个进程、多个连接，不用 JVM synchronized 代替跨实例控制。
- 新库使用自己的迁移历史，不复制 Core 的 flyway_schema_history；旧迁移文件保持不变。

产物：社区数据库新迁移、约束检查和原生 PostgreSQL 并发测试。通过条件：Community 无需访问 Core 数据库即可完成社区业务与并发控制。

## 第 7 步：落实可信身份、权限和用户展示信息

动作：
- 浏览器 Session、登录、注销、CSRF 和强制改密继续由 Core 入口处理。
- Core 先执行现有账号状态/安全版本检查，再以短期、面向 Community 的签名身份凭证调用 API；校验发行方、受众、有效期、签名和角色，拒绝客户端自报 userId/role。
- 社区 API 限制在可信服务访问路径，传输及服务身份受保护。普通浏览器不可绕过 Core 直接调用内部写接口。
- Community 必须独立检查内容所有权、管理员操作、可见性及状态转换。身份被验证并不意味着所有操作都有权限。
- 停用/角色变更后的用户在 Core 下一次请求被拒绝；记录短期内部凭证仍可能存在的在途窗口，不声称实现更强的即时跨服务撤销。
- Community 返回作者 ID；Core 使用已有用户模块批量补齐当前显示名，避免社区列表 N 条内容产生 N 次远程查询，也避免 Community 反向调用 Core 形成同步依赖环。

产物：认证接口设计、权限测试、账号变更和失效测试。通过条件：原三种角色行为一致，伪造身份和越权请求失败，列表显示名正确。

## 第 8 步：迁移社区业务并保留事务不变量

动作：
- 将社区领域、查询、写服务和 Repository 移入 Community；在新服务中建立 JSON API 控制器。
- 保留问题锁顺序、采纳条件更新、举报去重、审核竞争、隐藏与恢复等已实现约束。
- 将社区审核审计写入 Community 本地审计表，与审核动作同事务提交；不能改成不可靠的后台日志。
- Core 中由 CommunityClient 替换直接业务调用。先做查询，再做写入；路由切换前两种写路径不能同时对真实数据开放。
- 用架构检查禁止 Core 引用社区 Repository、实体内部实现或访问社区数据库；禁止 Community 引用 Core Repository/业务实现。

产物：社区业务 API、Core 客户端适配层、边界检查。通过条件：业务逻辑归属 Community，Core 只依赖协议，现有关键不变量在新服务测试中成立。

## 第 9 步：实现跨服务事件、通知和审计展示

动作：
- 以业务事件适配现有回答创建、采纳变化和内容隐藏通知；事件含稳定 eventId、类型、版本、聚合 ID、必要收件人和发生时间。
- Community 在业务事务内写 outbox，事务提交后发布器才能发送。不要仅把 ApplicationEventPublisher 换成一次 HTTP 请求。
- 第一阶段使用受保护的 Core 内部事件接收 API 即可，不强制增加消息中间件。Core 在一个本地事务中完成事件去重、通知任务和必要查询投影，提交后才确认成功。
- 发布器持久化失败次数、下次重试和最终失败状态；支持人工重放与积压监测。多实例发布器以租约/领取机制竞争任务，处理超时后可恢复。
- 通信语义采用至少一次投递加消费幂等；不承诺跨数据库 exactly-once，也不承诺外部邮件绝对不会重复。
- 对取消采纳/重新采纳、隐藏/恢复后再隐藏，事件身份必须代表具体动作，不能只用内容 ID 永久去重。
- 统一审计页面若保留跨业务总览，则通过只读投影或显式聚合保留全部来源；社区本地审计是事实来源。处理来源 ID 冲突、稳定排序、全局分页和迁移去重，不能只取两页拼接。
- 删除或停用原来针对同一社区动作的进程内通知监听路径，避免迁移后双发。

产物：outbox、事件接收去重、投递状态、审计查询适配。通过条件：回滚不发事件，重复投递不重复生成同一通知；接收端停机恢复后积压可处理，审计不丢失。

## 第 10 步：保持页面和核心维修可用

动作：
- 原社区 URL、模板、表单、CSRF、筛选、分页、错误提示和跳转按验收清单保留。
- Core 将 API 校验错误映射回原字段和页面，将超时、不可用与业务拒绝区分显示；失败时不能伪装写入成功。
- CommunityClient 配置连接/响应超时、有限连接池和并发隔离，避免社区不可用耗尽 Core 线程并拖垮维修业务。
- 检查全局导航、通知数量和管理员页面是否意外同步依赖社区；维修页面不应为渲染菜单而阻塞等待社区服务。
- 仅在有幂等保证时重试写请求；读请求的重试也应有限，避免故障时流量放大。

产物：页面集成、错误映射、故障隔离配置。通过条件：社区中断时社区页面清楚报告状态，维修功能在预定负载下继续通过。

## 第 11 步：演练数据迁移与回退

动作：
- 对源数据库做可恢复备份，在隔离副本完成迁移演练。
- 按约束依赖导入问题、回答、采纳、举报和社区审计；保留旧 ID、时间、作者引用、状态及审计来源标识。
- 修复目标序列，使新 ID 不与历史数据冲突；校验行数、关联、采纳有效性、隐藏内容、举报历史和抽样字段摘要。
- 核对 Core 原有通知链接指向迁移后仍存在的社区内容。
- 检查源库已有未完成通知任务和新 outbox 的交界，不重发历史业务事件；明确切换水位。
- 第一阶段允许短暂社区写维护窗口：暂停全部社区旧写入口，等待在途事务结束，完成最终同步和校验，再启用新服务写入。维修业务可继续运行。
- 回退分两种：新服务尚无新写入时可切回原路径；新服务已有写入后，必须暂停写入并导回增量、校验后回切，或选择向前修复。禁止直接切回过期数据。
- 旧表先保留、禁止旧应用继续写；验证备份和恢复后再安排未来清理，不在本次直接删除。

产物：迁移脚本、校验输出、切换和回退 runbook。通过条件：迁移和有新写入后的恢复均演练成功，只有一个权威写入路径。

## 第 12 步：完成拆分后的回归、契约和故障测试

动作：
- 执行第 2 步全部功能验收；Core 与 Community 分别执行单元和集成检查，补充跨服务契约与端到端验证。
- 原生 PostgreSQL 验证频率限制、采纳竞争、审核竞争、事务回滚和幂等；增加真正两个社区进程的关键并发场景。
- 模拟网络超时、服务重启、事件确认丢失、重复事件、outbox 发布器退出及过期租约恢复。
- 单独发布兼容的新 Community 版本，Core 不重新发布也能继续工作；使用版本/部署记录证明。
- 在停止 Community 的情况下执行维修核心验收；不要把“一次点击成功”当作高负载故障隔离证据。

产物：回归结果、契约结果、故障恢复记录、独立发布记录。通过条件：无新增功能回归和数据不变量破坏，所有未完成项明确标注。

## 第 13 步：建立真实的多实例部署拓扑

动作：
- Core 1 个实例；Community 分别配置 1、2、3 个等规格实例；社区内部 LB 配置实际后端列表、健康检查和连接排空。
- 所有 Community 实例连接同一个社区权威数据库，不各自保存一份互不一致的数据；身份、幂等和发帖限制不依赖某个实例内存。
- 不依赖固定 container_name 或单个固定宿主端口实现多副本；记录 LB upstream 与实际实例 ID。
- 验证流量确实到达多个后端，单实例停止后健康检查摘除，未完成写入通过数据库事务及幂等恢复。
- 社区服务之间无共享浏览器 Session，因此不必为社区副本复制 Core Session；若以后增加 Core 实例，则单独处理 Core 共享 Session、统一限流、附件共享和后台任务协调。
- Docker Desktop 可用于受控本地实验，但共享宿主机 CPU/内存必须记录；本地数据不可标为 AWS 实测。AWS 部署若实施，应使用独立的社区部署单元，演示服务级扩容而非复制整个组合应用。

产物：部署配置、资源限制、LB 后端和健康检查记录。通过条件：只改变社区副本数，Core 和数据库规格保持不变，流量分发和实例退出经过验证。

## 第 14 步：固定实验设计、数据和观测

动作：
- 每次记录提交 SHA/构建摘要、API 版本、环境、实例规格、数据库规格、连接池、LB、网络及压测机资源。
- 准备有代表性的用户、问题、回答和审核历史数据，具体规模在试跑后固定；正式对比期间不可改变。
- 设计浏览/搜索/详情为主的读场景、受控的提问/回答/审核写场景、以及核心维修与社区同时运行的混合场景。
- 主容量实验让不同用户操作不同内容；另设单热门问题竞争场景，区分数据库热点串行化与全局扩容能力。
- 所有配置使用同一数据快照、业务比例、索引与缓存策略，测试间恢复数据和预热状态。高压写入不要随意改动生产环境。
- 采集社区实例和 Core 的 CPU/内存/GC/线程/HTTP 连接池、DB 连接池等待；数据库 CPU/I/O/慢 SQL/锁等待/连接数；LB 分布；outbox 积压和事件延迟。
- 对比时固定每实例资源，记录总资源随实例数增加。若所有容器竞争同一固定宿主机，要说明资源争用及结论边界。

产物：实验计划、数据生成/恢复方式、固定策略和监测配置。通过条件：仅一个明确实验变量变化，其他差异可追踪。

## 第 15 步：执行相同压力与容量上限对比

动作：
- 先 smoke 验证脚本和真实内容，再预热；正式稳定阶段建议 5–10 分钟，每个配置至少重复 3 次并记录顺序与波动。这是本项目实验建议，不是通用认证标准。
- 第一组：在 1/2/3 个社区实例上施加相同到达率，比较各端点延迟、错误率和资源使用。低负载时吞吐相同是预期结果，不强求提升。
- 第二组：逐级提高到达率，找出每种实例数满足第 2 步全部目标的最大持续成功业务吞吐 Qn。
- 第三组：保持核心维修负载固定，提高社区负载，观察维修延迟与错误率、Core 资源和共享数据库资源。
- 分别测试社区 API 直达路径与浏览器所走的 Core→Community 完整路径；前者通过而后者无收益，只能声称社区后端扩容，不能声称端到端容量已提升。
- 使用 k6 constant-arrival-rate/ramping-arrival-rate 或同等开放负载模型，记录实际输入速率和 dropped_iterations。rate 表示场景迭代速率；一轮多请求时必须另外统计业务请求/秒或业务操作/秒，不混用单位。
- 压测机 CPU/网络、VU 配额或连接耗尽导致未发出的负载不得算成服务已成功承受；记录未完成、超时和内容校验失败。
- 不沿用“10 个 VU、每轮 3 次读取后睡 1 秒”脚本来搜索容量上限；旧报告约 27.78 请求/秒接近该闭合负载低延迟时的约 30 请求/秒理论上限，仅可作旧版本参考。

产物：各配置原始数据、逐端点摘要、资源时间线及重复实验结果。通过条件：数据可复现，报告成功业务吞吐而不是只报 HTTP 数量，不漏报失败或施压不足。

## 第 16 步：解释结果并修正瓶颈

动作：
- 扩容加速比 Sn = Qn / Q1；效率 En = Qn / (n × Q1)，其中 Qn 必须来自相同质量目标和场景下的最大可持续吞吐。
- 同时比较尾延迟、错误、资源和成本，记录重复实验波动；不以一次最好结果代表所有运行。
- 社区 CPU/线程饱和而数据库有余量时检查应用扩容收益；Core 饱和时检查页面渲染/客户端连接池/批量用户补齐；DB 饱和时检查 SQL、索引、锁、连接和 I/O。
- 更多应用实例会增加总连接池容量，可能压垮数据库；不能无限调大连接池，或把同时升级 DB 的结果算作只增加社区实例的收益。
- 需要优化时，每轮记录改动，只对新的版本重跑必要对比；保留原失败结果作为瓶颈证据。
- 如果只有 API 直达路径改善，先处理 Core 入口瓶颈或收窄结论；如果所有配置无明显收益，则继续调查，不以“已经是微服务”代替扩容证据。

产物：瓶颈解释、必要优化及复测。通过条件：可以解释扩容收益、开始下降的位置，以及尚未解决的共享资源限制。

## 第 17 步：分别说明水平、垂直与自动扩缩容

动作：
- 水平扩容：第 15 步只增加 Community 实例数；这是本阶段必交证据。
- 垂直扩容：如果实测，固定实例数、改变单实例 CPU/内存并另立实验；若不实测，写明仅解释设计，不给虚构数据。
- 自动扩缩容：不是第三种容量维度，而是按指标自动调整资源的控制机制。老师要求解释概念不等于要求必须部署自动扩缩容。
- 若实施自动扩缩容，明确社区 min/max、CPU/请求量/排队等指标、阈值、持续时间、冷却和回落规则；分别测升压、实例就绪/加入 LB、稳定及缩容排空。
- 手动改副本数只能证明水平扩容；不能标为已经验证自动扩缩容。未完成自动扩缩容时写清现状和后续计划。

产物：三个概念及项目映射；可选的自动扩缩容配置和时间线。通过条件：实际实现与设计说明分开，报告口径准确。

## 第 18 步：按老师反馈整理交付与演示

动作：
- 展示迁移前后拓扑、业务/数据所有权、API、身份和“回答→outbox→通知”时序，说明保留维修事务边界的原因。
- 演示独立构建/发布 Community，Core 版本保持不变；演示 Community 1→2→3，Core 副本数保持不变。
- 展示数据库隔离、禁止跨库访问、自动边界检查、功能回归与数据迁移记录。
- 展示 Throughput、p95/p99、Error Rate、应用/数据库资源和事件延迟；标清环境、数据规模、单位、重复次数和瓶颈。
- 演示社区实例退出与事件接收端短暂不可用后的恢复；验证维修业务仍可用。
- 如实说明尚未拆分的 Core、Core 入口和数据库的共享限制，以及未来何时需要抽离通知或其他服务。

最终门槛：两个服务独立部署且数据归属明确；社区独立水平扩容真实可用；功能和数据验收通过；扩容收益与瓶颈有可复现实验；未实现项目明确标注。达到门槛后再对外宣称迁移完成。
