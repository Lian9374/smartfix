- README、UI 指南、共享 CSS、公共导航：A 整合；各成员交自己的更新说明，避免五人同时改 README。
- 各角色概览和业务页面按所属模块主改；视觉规范由 A 发布，不集中搬给 A 重写。

### 事件／接口契约先冻结

- C→E：真实请求／工单状态、发生时间及可用于幂等的事件标识。
- B→C/E：有效指派、改派／撤回及对应事件的现有契约。
- A→E：社区事件和收件人规则，尤其自我回答／采纳等规则不擅自变化。
- E→D：SLA 只读结果与不可用状态，字段依据模型确定，本文不凭空规定接口路径。

没有接口依赖的 UI、权限、附件、测量和测试可先独立推进。通知／SLA／报表端到端集成仍存在真实依赖，不能承诺五个人完全互不影响。

## 4. 执行顺序与合并策略

阶段 1 — 基线与契约：A 建缺陷／发布清单；C 先交迁移兼容修复验证及编号登记；B 验权限基线；D 做性能与体验基线；E 冻结投递及 SLA 契约。无需等待所有业务收口才开始独立检查。

阶段 2 — 独立实现：五人各自修所属模块；E 按通知、附件、SLA、邮件顺序交小 PR。每个 PR 自带测试与交接，不把整个 E 包绑成一个无法评审的大 PR。

阶段 3 — 接口联调：先整合受评审的迁移修复，再整合权限／生命周期及模块整改；新增配置和迁移通过唯一负责人协调。最后验证事件投递、SLA、下游报表。

阶段 4 — A 主导发布验收：固定 SHA，运行统一验证，完成实际页面／真机／读屏检查，登记阻塞和已知限制。若 SLA／邮件尚未交付，明确“遗留未完成”，不得写全范围完成。

建议各人使用独立分支，如 `feature/sprint4-usera-release-quality`、`feature/sprint4-userb-access-dispatch`、`feature/sprint4-userc-migration-workflow`、`feature/sprint4-userd-map-reporting`、`feature/sprint4-usere-delivery-reliability`。这些名称是建议，本文没有创建分支、PR 或推送代码。

评审建议：B 复核权限／账号相关修改；C 复核所有新增迁移；E 复核事件投递；D 复核 SLA 报表消费；A 复核视觉／验收材料。负责人不能把自己的测试写成其他人已批准。

不强行承诺每人相等工时或完成天数；首先按已知缺陷和 E 的遗留规模估算，再确定日程。

## 5. 共同完成标准

- 功能接真实代码与数据库，不加假按钮、假数据或临时绕过权限。
- 各负责人提交有意义的模块测试；并发、迁移和数据库约束使用真实 PostgreSQL 验证。
- 最终版本运行 `mvn -o -DskipTests compile`、`mvn -o -B verify`，以及配置专用测试库后的 `mvn -o -B -Ppostgres-it verify`。离线依赖不足时记录原因，不把失败写成通过；按项目测试指南配置专用测试环境。
- 浏览器验收复用 `tools/verify-community-browser.mjs` 和 `tools/verify-role-workspaces-browser.mjs`；设置各自要求的独立验收库，记录覆盖与遗漏。
- 前端按实际 Thymeleaf／静态脚本检查；对修改脚本做 `node --check`，不假设项目存在 React 前端构建。
- `git diff --check` 通过；共享文件和迁移完成指定评审。
- 测试证据记录命令、时间、SHA、环境、结果、失败／跳过原因；历史结果不能当成本轮执行结果。
- 未完成项有责任人、影响、处置和范围结论；缺配置、缺实际设备或缺外部通道时如实登记。
- 各成员交接到位后，A 发布最终非 AWS 验收结论。AWS 仍须后续独立部署与验收。
